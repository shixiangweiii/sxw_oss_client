# 同步覆盖二次确认实施方案与改动说明

- 整理日期：2026-09-05
- 项目：OSS Client（`sxw_oss_client`）
- 状态：功能已实现，自动测试与 Electron 窗口验证已完成。
- 整理依据：本次需求讨论、已确认的实施方案、当前工作区实现及本次实施阶段的实际验证结果。

## 1. 需求与最终确认结果

本次改动用于个人使用的本地目录与阿里云 OSS 双向同步工具，目标是在覆盖更新的目标文件前逐个取得用户确认，同时自动跳过内容相同的文件。

最终规则为：**先比较内容；内容相同自动跳过；内容不同且目标文件修改时间晚于来源文件时，逐个弹窗确认。**

| 同步方向    | 来源     | 目标     | 需要确认的条件                   |
| ----------- | -------- | -------- | -------------------------------- |
| 本地 → 云端 | 本地文件 | 云端对象 | 内容不同，且云端修改时间晚于本地 |
| 云端 → 本地 | 云端对象 | 本地文件 | 内容不同，且本地修改时间晚于云端 |

弹窗按用户确认的要求提供三个操作：

| 操作         | 当前文件                           | 后续文件                     |
| ------------ | ---------------------------------- | ---------------------------- |
| 确认覆盖     | 使用来源内容覆盖目标               | 继续同步，后续冲突仍单独确认 |
| 跳过此文件   | 保留目标内容                       | 继续同步                     |
| 取消本次同步 | 不覆盖当前待确认文件，清理临时文件 | 结束任务，已完成的文件保留   |

默认焦点和 Esc 对应“跳过此文件”。用户关闭确认框按跳过处理；因任务取消或窗口生命周期协调而由程序收起确认框，不能记为用户跳过。

等待确认没有自动通过的超时，同一时刻只处理一个文件的确认。

## 2. 原有基础与本次新增能力

原有同步已具备实际内容的 SHA-256 比较、同内容跳过、逐文件顺序处理、上传稳定快照、下载临时文件与原子替换、任务取消及临时文件清理机制。

因此，**SHA-256 比较是本次复用的既有能力，并非新加入的 Hash 算法**。本次主要增加：

1. 从 OSS HEAD 响应读取最后修改时间。
2. 内容不同时按两端时间决定是否请求确认。
3. 主进程异步原生确认框及等待状态。
4. 等待确认与取消、关闭、退出、刷新之间的协调。
5. 用户跳过的原因记录及完成文案调整。
6. 对应的服务、状态、运行时和 Electron 回归测试。

### 2.1 OSS 时间与 Hash 的选择依据

OSS `HeadObject` 返回 `Last-Modified`，可在不下载内容的情况下取得对象最后修改时间。实现复用已有的 `client.head()` 请求，通过 `head.res.headers['last-modified']` 读取该值。[阿里云 HeadObject 文档](https://help.aliyun.com/zh/oss/developer-reference/headobject)

OSS 的最后修改时间由服务端维护，反映云端对象的更新时间，不自动保留源文件的本地修改时间。上传覆盖或部分元数据修改会更新该时间。[阿里云文件元数据说明](https://help.aliyun.com/zh/oss/user-guide/manage-object-metadata-10)、[LastModified 更新操作说明](https://help.aliyun.com/zh/oss/user-guide/what-are-the-operations-that-affect-the-lastmodified-attribute-of-oss-objects)

例如，本地文件 10:00 修改，10:05 上传后，两边内容相同但云端时间更晚。本次规则会先判断内容相同并跳过，不再进入时间确认。

内容比较继续使用原始字节的 SHA-256。OSS ETag 的含义与上传方式有关，不能统一作为内容 MD5 使用；当前读取中的 ETag 仍用于已有的 `If-Match` 条件读取。[阿里云数据一致性校验说明](https://help.aliyun.com/en/oss/user-guide/data-verification/)

## 3. 判断规则与数据流程

### 3.1 统一判断矩阵

| 目标状态 | 内容判断                | 时间判断         | 结果                                   |
| -------- | ----------------------- | ---------------- | -------------------------------------- |
| 不存在   | 无需比较                | 无需比较         | 直接创建                               |
| 已存在   | 大小相同且 SHA-256 相同 | 无需比较         | 自动跳过                               |
| 已存在   | 内容不同                | 目标较新         | 请求逐文件确认                         |
| 已存在   | 内容不同                | 目标较旧或同秒   | 直接更新                               |
| 已存在   | 内容不同                | 无法取得有效时间 | 保留目标，记录该文件失败，继续其他文件 |

先比较大小：大小不同直接判定内容不同；大小相同时才读取两端内容比较 SHA-256。内容相同的文件不受时间差异或时间字段无效影响。

### 3.2 时间口径

- 云端使用已有 HEAD 响应中的 `Last-Modified`，不依赖列表展示时间。
- 上传使用本次本地快照对应的源文件 `mtime`。
- 下载使用同步开始处理该文件时取得的本地目标 `mtime`。
- 将两端时间转换为 Unix 时间后，使用 `Math.floor(milliseconds / 1000)` 按整秒比较；同一秒视为时间相同。
- 弹窗按电脑本地时区显示日期、时间和时区。
- 无法解析的云端时间记为 `null`，需要进行覆盖时间判断时报告错误，不用零值或当前时间替代。

### 3.3 上传流程

```text
建立本地稳定快照并计算 SHA-256
  → HEAD 查询云端目标
  → 若目标存在且大小相同，读取云端内容计算 SHA-256
  → 内容相同：自动跳过
  → 内容不同：比较修改时间，必要时等待确认
  → 确认覆盖或无需确认：普通上传 / 分片上传
  → 清理临时快照
```

确认前不会调用普通上传，也不会初始化分片上传。用户跳过或取消时，当前上传快照会进入既有清理流程。

上传仍以本轮稳定快照为准；快照建立后的来源编辑留到下一轮同步，不在上传过程中混入新内容。

### 3.4 下载流程

| 场景               | 执行顺序                                                                                            |
| ------------------ | --------------------------------------------------------------------------------------------------- |
| 目标不存在         | 下载到临时文件，成功后替换到目标位置                                                                |
| 目标存在且大小不同 | 比较时间，必要时确认，再下载并替换                                                                  |
| 目标存在且大小相同 | 下载到临时文件并计算 Hash，与本地比较；相同则跳过，不同则比较时间并按需确认；确认后复用临时文件替换 |

大小相同的文件可能需要先下载完整内容才能判断是否跳过。**跳过更新不等于没有云端读取流量**；确认前写入的是临时文件，不是目标文件。

下载保留既有的目标状态复核，并在同大小文件完成本地 Hash 读取后检查是否仍对应原目标快照。若目标在读取或等待确认期间发生变化，则保留当前目标并报告该文件失败。

## 4. 接口、状态与原生弹窗

### 4.1 同步服务接口

在 `src/main/sync.ts` 增加确认请求与回调类型：

```ts
export interface SyncConfirmation {
  taskId: string
  direction: SyncDirection
  bucket: string
  key: string
  localPath: string
  localModifiedAt: number
  remoteModifiedAt: number
}

export type ConfirmOverwrite = (
  request: SyncConfirmation,
  signal: AbortSignal
) => Promise<'overwrite' | 'skip' | 'cancel'>
```

`SyncManager.start(direction, connection, confirm)` 的第三个参数为必传回调；缺失时拒绝启动，不默认允许覆盖。共享的 `confirmIfNewer()` 负责时间判断、等待状态、选择结果处理与取消检查。

该回调是主进程内部接口。原生弹窗直接将选择返回同步服务，本次没有新增确认专用 IPC，也没有扩展 preload 暴露的 `ElectronAPI` 方法。

### 4.2 状态变化

- `SyncPhase` 增加 `confirming`。
- `isSyncActive()` 将 `confirming` 视为进行中，保持重复同步、在线保存等原有互斥约束。
- 进入等待状态时立即广播，界面显示“等待覆盖确认”。
- 等待期间不增加 `processed`，不开始下一个文件。
- 覆盖确认通过后恢复处理；取消后进入既有取消与清理流程。

### 4.3 原生弹窗

`src/main/syncRuntime.ts` 的 `confirmationFor()` 负责调用绑定发起窗口的 `dialog.showMessageBox()`。必要时恢复、显示并聚焦该窗口，其他窗口只显示共享任务状态。

展示内容包括文件 Key、覆盖方向、本地完整路径、`oss://bucket/key` 云端位置和两端修改时间。按钮与返回值对应为：

| 返回索引 | 文案         | 服务决定    |
| -------- | ------------ | ----------- |
| 0        | 跳过此文件   | `skip`      |
| 1        | 确认覆盖     | `overwrite` |
| 2        | 取消本次同步 | `cancel`    |

`defaultId` 和 `cancelId` 均设置为 0。无效选择或弹窗处理异常会进入文件失败流程，保留目标。

使用 `AbortSignal` 关闭原生弹窗。macOS 下该机制要求弹窗绑定父窗口，本次实现明确绑定发起同步的窗口。[Electron dialog 文档](https://www.electronjs.org/docs/latest/api/dialog)

## 5. 取消、窗口生命周期与结果统计

### 5.1 取消与窗口协调

同步服务等待用户选择时同时监听取消信号。即使确认处理器没有及时返回，也能结束服务等待；迟到的覆盖选择不会继续写入。

运行时通过 `activeConfirmation` 管理正在展示的原生弹窗，通过 `exitDecision` 暂停和恢复覆盖确认，通过 `pendingExit` 防止重复退出流程。

关闭、退出或刷新发生在覆盖确认期间时，按以下顺序处理：

1. 程序临时收起覆盖弹窗，等待该弹窗关闭，保留当前文件的决定等待。
2. 展示原有的“继续同步 / 取消同步后继续操作”提示。
3. 选择继续同步后恢复同一个文件的覆盖确认，不增加跳过或已处理计数。
4. 选择取消后终止任务，等待临时文件清理和相关弹窗关闭，再执行关闭、退出或刷新；已有编辑草稿保护继续生效。

发起窗口异常销毁会取消任务。任务结束后移除该窗口的销毁监听；当前确认或退出流程尚未结束时，运行时拒绝启动新任务。

### 5.2 统计与显示

| 结果                         | 计数             | 说明                                       |
| ---------------------------- | ---------------- | ------------------------------------------ |
| 内容相同                     | `unchanged`      | 沿用“内容相同”统计                         |
| 用户主动跳过                 | `skipped`        | 详情记录“云端／本地文件较新，用户选择跳过” |
| 实际覆盖成功                 | `overwritten`    | 写入成功后才累计                           |
| 取消当前等待                 | 不计为覆盖或跳过 | 任务结束为取消                             |
| 时间无效、确认失败或目标变化 | `failed`         | 保留目标，记录错误并继续其他文件           |

用户跳过沿用既有 `skipped` 字段，没有新增独立计数；通过详情与其他路径冲突等跳过原因区分。已有的空目录计数规则也继续沿用。

保持以下计数关系：

```text
processed = created + overwritten + unchanged + skipped + failed
```

无错误但存在用户跳过时仍可正常完成。面板将“全部成功”改为“已完成”，将“其他跳过”改为“已跳过”，避免让用户误以为所有文件都已覆盖。

## 8. 保持的约定与适用范围

- 按个人工具需求处理，不增加多人编辑协调、时钟偏差补偿或历史同步基线。
- 普通文件使用本次确认规则；空目录、符号链接、特殊文件、越界路径和名称冲突沿用既有处理。
- 不传播删除，不增加定时同步、文件监听或批量确认。
- 下载不额外复制云端修改时间；同内容跳过不更改目标修改时间。
- 上传以本轮稳定快照为准；保留已有读取版本条件和本地文件一致性检查，不提供跨客户端原子覆盖保证。
- 用户确认只允许执行当前文件的更新；后续文件若目标更新，仍需再次确认。
- 临时文件清理失败继续单独记录，不把已经成功的覆盖改计为失败。
