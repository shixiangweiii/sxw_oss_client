## 一、结论

**没有发现需要在合入前修复的正确性缺陷。** 排除规则只作用于上传扫描，命中目录会停止下探；确认前不会 PUT、创建云端目录对象或初始化分片；预览等待占用同步互斥，`previewing` 计入活跃同步；决定只能消费一次，迟到决定和其他窗口不能启动上传。`uploadMode` 每次任务重置，一键模式只跳过上传方向的修改时间确认，内容相同、合并标记、快照和路径检查仍然执行。

## 二、已核对且与规格一致的行为

| 关注点 | 核对结果 |
| --- | --- |
| 规则语法 | `parseSyncIgnore` 按逗号拆分、去空白、去空项、去重。`*` / `?` 不跨越 `/`，`**` 必须是独立路径分量。单段规则自动加前缀 `**`，因而 `.git` 匹配任意层级且不匹配 `.github`。前导 `/` 只从同步根匹配，尾部 `/` 只匹配目录。`docs/private/**` 能剪枝 `docs/private` 目录，同路径普通文件不命中。无效的空段、`.`、`..`、NUL 在 `SyncIgnore` 构造时抛错，任务失败，不静默丢规则。 |
| 扫描剪枝 | `localEntries` 仅在上传方向调用。名称规则在 `stat` 前排除；目录规则在确认类型后 `continue`，不再 `visit`。只含排除项的目录不会变成空目录标记。空目录、符号链接、临时目录和扫描错误仍走原分支。 |
| 候选与执行 | 预览只收 `kind !== 'skip'`、非扫描错误、非名称冲突的项。确认后继续遍历同一次 `entries`，不重新扫描。冲突、符号链接和扫描错误仍在原循环里记跳过或失败，所以任务总数可以大于候选数。 |
| 确认前写入 | 预览之前仍有残留恢复、卷规则探测和云端列举。PUT、空目录对象和分片初始化都在 `upload()` 里，位于 `waitForUpload` 返回 `normal` 或 `overwrite-all` 之后。 |
| 两种确认 | 内容相同在 `confirmIfNewer` 之前返回。一键模式在 `sync.ts` 的修改时间判断处直接返回，不绕过合并标记、快照、`safePath` 和空目录复核。下载方向不读 `uploadMode`。`start()` 每次把 `uploadMode` 置为 `null`。 |
| 等待与取消 | `waitForUpload` 自己监听 `AbortSignal`。主进程 `pendingUpload` 在决定或取消时清掉。其他窗口、旧 `taskId`、非法决定和重复确认返回结构化错误。预览查询每次 `slice` 最多 100 项，状态广播不带完整列表。 |
| 互斥与关闭 | `reserveSync` 在整个 `run()` 结束前不释放，预览包括在内。`isSyncActive` 含 `previewing`，关闭、退出和 `beforeunload` 仍走 `manager.active`。没有候选项时不进入 `previewing`，面板保留“没有可同步的文件”的提示。 |
| 进程边界 | 新通道已登记在 `constants.ts`、`ElectronAPI`、`syncRuntime.ts` 和 `preload/index.ts`。preload 只桥接具名 IPC。渲染层收到的是路径、大小和汇总。 |
| 界面 | `UploadPreview` 在 `showModal()` 之后把焦点放到“取消”。Esc、关闭图标和取消按钮都提交 `cancel`。重复提交由 ref 挡住。请求序号让过期分页结果失效。任务面板有 `previewing` 文案，并在本轮 `overwrite-all` 时说明不再逐文件询问。 |

`scripts/tests/sync-ignore.test.mjs` 覆盖了变更记录里的语法表（含 `docs/private` 的目录与同名文件、换行文件名、字面方括号）。服务测试覆盖忽略目录不上传、确认前无写入、取消与迟到决定、一键覆盖不跨任务。这些断言和当前源码一致；本轮没有重新执行它们。

## 三、建议（非阻塞）

### 1. macOS 上 NFD 文件名和 NFC 规则对不上（`src/main/syncIgnore.ts:61`）

段比较是 `part.test(names[i])`，规则和 `readdir` 名称都按 JavaScript 字符串原样使用，没有做 Unicode 规范化。

macOS 上 `readdir` 通常返回 NFD。用户写在 `.env` 里的规则通常是输入法产生的 NFC。带组合字符的名称会对不上，文件仍进入预览并上传。本次用当前源码探针的结果：

| 规则（NFC） | 磁盘名（NFD） | 两者字符串相等 | NFD 名称是否命中 |
| --- | --- | --- | --- |
| `café.txt` | `cafe` + U+0301 + `.txt` | 否 | 否 |
| `が.txt` | `か` + U+3099 + `.txt` | 否 | 否 |
| `文档.txt` | 同一串 | 是 | 是 |
| `.git` | 同一串 | 是 | 是 |

大小写敏感、隐藏名和 `u` 标志下 `?` 匹配一个码位都是对的。现有冲突检测在 `sync.ts` 的 `conflicts()` 里，会在卷不区分规范化时把名称转成 NFD；排除规则没有沿用这个约束。变更记录的 P1 验收包含中文名，常见汉字没有 NFD 分解，这条路径目前是安全的。带附加符号的拉丁文、日文浊音等会漏排除。

**建议**：编译规则段和比较扫描到的名称之前，两边都规范成 NFC。这样字面规则能对上磁盘上的 NFD 名称，`?` 仍然表示一个组合后的字符。不要先把文件名拆成 NFD 再交给 `?`，否则一个 `é` 会变成两个码位。保持大小写敏感。
