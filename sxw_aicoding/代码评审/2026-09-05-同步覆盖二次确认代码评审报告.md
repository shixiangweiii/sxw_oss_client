## 4. 问题清单

严重程度从高到低：M（中等，建议下轮修复）> L（低，可择机处理）。

### M1.（中等）退出/关窗守卫与启动守卫的防御口径不一致

- 位置：`src/main/syncRuntime.ts:155`、`167`（`close` / `before-quit` 守卫）对比 `src/main/syncRuntime.ts:190`（启动守卫）。
- 现象：`OSS_SYNC_START` 在 `pendingExit || activeConfirmation` 时拒绝启动；但 `close` 与 `before-quit` 的守卫只检查 `!manager.active && !pendingExit`，不检查 `activeConfirmation`。
- 时序窗口：用户选择「取消本次同步」（或面板取消）→ 任务 signal abort → `confirmIfNewer` 立即 reject → 任务完成清理、`manager.active` 变为 false，但原生弹窗 dismiss 仍在途、`activeConfirmation` 尚未清空。此瞬间退出/关窗会绕过 `deferExit` 直接执行。
- 影响：有限。该确认的答案本就会被丢弃、任务已结束，无数据安全风险；但与方案「当前确认或退出流程尚未结束时，运行时拒绝启动新任务」的防御意图不对称——start 挡了，quit/close 没挡。
- 建议：`close` / `before-quit` 守卫统一改为同时检查 `activeConfirmation`。

### L1.（低）上传确认基于 HEAD 时刻的时间快照，确认等待期间无再校验

- 位置：`src/main/sync.ts:619-628`。
- 现象：用户在确认框等待期间，云端对象可能被其他客户端覆盖；用户基于过期时间确认后 `client.put` 无条件写入。同大小下载比较有 `If-Match` 保护，上传覆盖没有。
- 定性：方案第 8 节已声明「不提供跨客户端原子覆盖保证」，属已知边界，非缺陷。
- 建议：至少在 README 或弹窗文案中显式提示（README 目前仅隐含在「外部客户端并发写入的最终结果取决于提交顺序」一句中）。

### L2.（低）`key: state.currentFile!` 的隐式耦合

- 位置：`src/main/sync.ts:427`。
- 现象：`confirmIfNewer` 从 `state.currentFile` 取 key，依赖 run 循环先调用 `step('comparing', entry.key)` 的调用顺序。测试被迫手工伪造 `f.manager.state.currentFile / direction`（`sync.test.mjs:929-930`）才能直调 `download()/upload()`，内部耦合已渗入测试。
- 建议：将 key / direction 作为显式参数传入 `confirmIfNewer`，降低对 `this.state` 副作用的依赖。

### L3.（低）`response` 判断与 abort 标志的顺序依赖缺注释

- 位置：`src/main/syncRuntime.ts`（`confirmationFor` 内，`if (controller.signal.aborted) continue` 与 `response === 0/1/2` 判断）。
- 现象：Electron 在 `signal` abort 时 `showMessageBox` 以 `response: -1` 兑现；测试 mock 用 `cancelId`（即 0）模拟，与真实返回值不同。当前代码先查 `controller.signal.aborted` 再查 `response`，两者都被正确消解；但正确性完全依赖这一先后关系。
- 建议：加一行注释说明「abort 兑现值（-1 / mock 的 cancelId）必须先于 response 分发被拦截」，防止后人重排判断顺序。

### L4.（低）同步块不变量脆弱，缺保护性注释

- 位置：`src/main/syncRuntime.ts:16-31`（`if (exitDecision) await exitDecision.promise` 之后到 `activeConfirmation = current` 之间）。
- 现象：「`exitDecision` 非空时不得展示覆盖弹窗」这一不变量目前靠单线程事件循环下该段无 await 维持；将来任何人在其间插入一个 await，就会出现退出确认框叠加覆盖确认框。
- 建议：注释标注「此处到 `activeConfirmation` 赋值前不得引入 await」。

### L5.（低）启动拒绝的错误文案不准确

- 位置：`src/main/syncRuntime.ts:190`。
- 现象：`pendingExit` 为真但并无确认框时（例如退出决策进行中、覆盖确认尚未开始），也提示「请等待当前确认窗口关闭」。
- 建议：按 `pendingExit` / `activeConfirmation` 分别给出文案，如「请等待当前退出确认完成」。

### L6.（低）每次确认 `win.show(); win.focus()` 抢焦点

- 位置：`src/main/syncRuntime.ts:19-21`。
- 现象：多冲突文件时连续弹窗 + 连续抢焦点，用户切走后会被反复拉回。
- 定性：符合方案「必要时恢复、显示并聚焦该窗口」，属设计取舍；仅提示实际使用体感。
- 可选优化：仅首次抢焦点，后续仅 `focus()`；或在弹窗中显示剩余待确认数量。

### L7.（低）不可达的防御分支

- 位置：`src/main/sync.ts:415`（`!Number.isFinite(localModifiedAt)`）。
- 现象：stat 的 `mtimeMs` 恒为有限数，该分支实际不可达。无害的防御性代码，可留可删。

### L8.（低）README 文档小瑕疵

- 位置：README 末段「……不触碰真实同步目录或真实 Bucket。 构建后可执行……」。
- 现象：句号后多一个空格，且新增句子被合并进原有段落，可读性略降。建议另起一段。

## 5. 值得肯定的实现细节

- **取消不死锁的关键设计**：`confirmIfNewer` 的 abort 包装（`sync.ts:436-453`）让任务取消即使 UI 处理器不返回也能释放等待，且迟到的 overwrite 被丢弃——这避免了「decide 等 task、task 等 handler、handler 等 exitDecision」的环状等待，代码注释也点明了意图。
- **同大小下载只读一次云端**：确认后复用已下载的临时文件，`gets` 请求数有测试断言锁死。
- **取消语义细致**：`checkCancelled` 补在 `chmod` 与 `rename` 之间（`sync.ts:522`），确认后才做的本地权限修改不会在取消后继续落地。
- **测试质量高**：双向 × 内容 × 时间矩阵、取消竞态、无效时间、目标变化、分片前置确认、多窗口共享状态、真实 SDK + 真实 Electron IPC + 原生弹窗专项；mock 的 abort 行为差异（`cancelId` vs `-1`）恰好被 `controller.signal.aborted` 前置判断消解。
