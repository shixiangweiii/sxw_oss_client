## 三、发现的问题与建议（按重要程度排序）

### P1（高 · 功能性）异步 diff 的「5 秒预算」实际是约 4000 行差异的上限

- **位置**：`src/main/textMerge.ts:81-85`（`diffLines(a, b, { timeout, callback })`）
- **原因**：jsdiff 的异步模式（`node_modules/diff/libcjs/diff/base.js`）每个 `setTimeout(…, 0)` 只执行**一次**编辑距离迭代，而 Node 的 `setTimeout(0)` 至少延迟 1 ms。所以 5 秒预算衡量的是定时器 tick 数，不是计算量：实测约 1.2 ms 才推进一个编辑距离，与文件大小和 CPU 无关。
- **实测**（`/tmp` 脚本，直接调用仓库的 `mergeText`）：

  | 场景                               | 输入大小 | 结果                      | 耗时     |
  | ---------------------------------- | -------- | ------------------------- | -------- |
  | 空本地 vs 云端 3000 行             | 16 KB    | 成功                      | 3590 ms  |
  | 空本地 vs 云端 8000 行             | 46 KB    | **超出 5 秒预算，未合并** | 5008 ms  |
  | 共同 2 万行 + 云端追加 3000 行     | 391 KB   | 成功                      | 3632 ms  |
  | 共同 2 万行 + 云端追加 8000 行     | 430 KB   | **超出 5 秒预算，未合并** | 5032 ms  |
  | 对照：同步模式计算上面两个失败场景 | —        | 成功                      | 11–21 ms |

- **影响**：两侧行级编辑距离（删除行数 + 新增行数）超过约 4000 的文件一律无法合并，即使只有几十 KB。方案承诺的是 5 MB 以内可合并，而日志、数据类文本追加几千行很常见。即使能合并也要多花数秒，并且串行执行：100 个约 3000 行差异的文件要多花约 6 分钟；超时的文件每个都要等满 5 秒。README 第 141 行「逐文件异步计算，预算 5 秒」的描述与实际效果不符。
- **测试缺口**：`text-merge.test.mjs:63` 用 `timeout = -1` 只验证了「立即超时」这条路径，没有任何真实规模的用例，所以问题没有暴露。
- **建议**：
  1. 首选：在 `worker_threads` 中用**同步**的 `diffLines(a, b, { timeout: 5000 })` 计算。这样预算是真实的 CPU 时间，主进程事件循环不阻塞，取消可以直接 `worker.terminate()`，也就不必再「等待算法收尾」。
  2. 备选：自己实现时间片，每个 tick 连续跑满约 10 ms 的迭代后再 `setImmediate` 让出。
  3. 补一条规模测试，例如「单侧追加 1 万行必须在预算内合并成功」。

### P2（中）「内容相同」的文件执行时不复核云端，云端后续更新被静默报告为「内容相同」

- **位置**：`src/main/sync.ts:585`（`if (checked?.kind === 'same') return 'unchanged'`）
- **复现**：`a.txt` 两端相同，`b.txt` 不同（触发弹窗）；在等待选择期间更新云端 `a.txt`，然后选择「按原规则同步」。结果：`phase: success`、`unchanged: 1`、详情为空，本地 `a.txt` 仍是旧内容。
- **对照**：改动前，执行阶段每个文件都会 HEAD 并与列举时的 ETag 比较，这种情况会报「对象在扫描后发生变化，请重新同步」。方案行为矩阵也要求「执行前版本变化 → 保留本地，记录失败」。云端对象在预检查后被删除的情况同样会被报告为「内容相同」。
- **风险**：预检查到执行之间可能隔着任意长的弹窗等待。用户看到「已完成 · 内容相同」，实际拿到的是旧文件。
- **建议**：在 `same` 分支前 HEAD 一次并调用 `assertRemote`，每个文件只多一次 HEAD，不需要 GET。现有「预检查后…变化」用例（`sync.test.mjs:1324`）只覆盖 different 文件，需要补充 same 文件的场景。

### P3（中低）合并模式下，「云端目录标记 + 本地同名普通文件」被误报为失败

- **位置**：`src/main/syncPrecheck.ts:115-118`（`entry.kind === 'directory'` 时不检查本地类型，直接记为 `directory`）；`src/main/sync.ts:586`（只凭 `checked.local.isFile()` 就进入 `mergeDownload`）
- **复现**：云端有 `foo/`（0 字节目录标记），本地 `foo` 是普通文件：
  - 选择合并：`failed +1`，详情为「重新读取的内容与预检查不一致，已保留本地文件」，任务变为「部分失败」，并多发一次 HEAD + GET；
  - 选择原规则：`skipped +1`，详情为「文件与目录同名冲突」（正确）。
- **数据安全**：不会写盘，因为指纹与 `undefined` 比较必然失败。问题在于分类和提示错误。
- **建议**：`inspect` 的 directory 分支要求本地也是目录，否则抛出 `SyncSkip('文件与目录同名冲突')`；或者合并分支的条件收紧为 `entry.kind === 'file' && checked.kind === 'different'`。

### P4（低）弹窗统计重复计数

- **位置**：`src/main/syncPrecheck.ts:148`，`this.summary.different++` 在解码和标记检查**之前**执行
- **复现**：只有一个无效 UTF-8 文件时，弹窗统计为 `{"different":1,"unavailable":1}`，显示「文本内容不同：1；无法合并：1」。含专用标记的文件同样如此。现有用例（`sync.test.mjs:1262`）只断言了 `unavailable`。
- **另外**：大小写 / Unicode 冲突条目的 `conflicts()` 在选择**之后**才计算（`sync.ts:402`），这些条目也会进入弹窗统计，执行时才被跳过。
- **建议**：把 `different++` 移到 `record.kind = 'different'` 之前；或把文案改成「其中无法合并 N」。可以考虑在弹窗前先计算 `conflicts`。

### P5（低）合并模式把内容相同的非文本 / 超限文本记为「已跳过」；相同的超过 5 MB 的文本每次都触发弹窗

- **位置**：`src/main/syncPrecheck.ts:120-125`、`src/main/sync.ts:586-592`
- **复现**：两端内容相同的 `img.png` 和一个 5 MB + 1 字节的 `big.log`：弹窗统计 `unavailable: 1`，弹窗仅由这个未变化的日志触发；选择合并后 `skipped: 2`，原因分别是「已有非文本文件不参与合并」和「两侧文本各须不超过 5 MB」。
- **影响**：与方案矩阵第一行「两端原始字节相同 → 跳过（内容相同），两模式相同」不一致。同步目录里只要有一个未变化的大日志，每次「同步到本地」都会弹窗；大量未变化的图片会在详情里产生同样数量的跳过记录。
- **建议**：预检查对超限文本和非文本可以「大小相同再流式计算 hash」判断是否相同（不受 5 MB 限制），相同则记为 `same`，也不计入 `unavailable`。或者至少在合并模式执行时，先走原流程「同大小比 hash → unchanged」，再决定是否跳过。

### P6（低 · 性能）上传前的标记扫描逐字符执行，比读取慢约 30 倍，未变化的文件也要扫描

- **位置**：`src/main/textMerge.ts:39-63`、`src/main/sync.ts:781-782`
- **实测**：200 MB 的 `.log` 文件，纯读取 231 ms，`fileHasMergeMarkers` 耗时 7147 ms（约 28 MB/s）。`log / sql / json / xml` 都属于文本扩展名，GB 级文件上传会多出分钟级耗时。扫描发生在「与云端 hash 相同 → unchanged」之前，所以未变化的文件也要付出这个成本。
- **建议**：在 Buffer 层用 `indexOf` 搜索三个标记的 UTF-8 字节序列，再判断是否位于行首；或者把检测并入 `snapshotFile` 的 hash Transform，一次遍历完成。检测也可以移到「与云端相同则 unchanged」之后。

### P7（低 · 体验）选择前看不到具体文件；选择取消后检查结果全部丢失

- **现状**：预检查中 unsupported / failed 的文件只在执行阶段才写入详情，弹窗只给数字。用户选择「取消本次同步」后，详情为空（复现 P4 时详情即为空），因此无法知道哪些文件无法合并、检查失败的原因是什么，也拿不到 requestId。另外，逐文件的预检查失败在详情中显示为「比较」阶段，`issueStages.prechecking` 实际只在致命错误时用到。
- **建议**：在预检查阶段就把 unsupported / failed 写入详情（phase 为 `prechecking`）；弹窗 detail 可以附上前 N 个路径。

### P8（低 · 性能）预检查串行执行；原规则下载每个文件新增一次 HEAD

- **预检查串行**（`sync.ts:372-376`）：每个两端都存在的文本文件依次 HEAD + GET，而 Diff 扫描用 3 并发。大 Bucket 首次弹窗前的等待会明显变长。
- **最终 HEAD**（`sync.ts:644-650`）：GET 已带 `If-Match`，缓存路径也已经过 `assertRemote`。最终 HEAD 与 rename 之间仍有时间窗口，安全增益有限，却让所有下载（包括新增文件和二进制文件）都多一次请求。
- **建议**：预检查改为 3 并发；评估去掉最终 HEAD，或只在复用预检查缓存的路径保留。

## 五、值得肯定的实现细节

1. **一致性校验链条完整**：本地 dev / ino / size / mtimeNs / ctimeNs + SHA-256，云端 ETag / versionId；缓存淘汰后重读仍比对指纹；「原本缺失、后来出现」同样拒绝写入。有覆盖本地 / 云端 / 缺失 × 两种模式的矩阵测试。
2. **合并提交路径安全**：同目录受管理临时文件 → 保留权限 → 复核两端 → `rename`。提交成功与清理失败分别计数，任务显示部分失败但不改写结果分类。
3. **取消语义严谨**：`chooseMode` 与 `confirmIfNewer` 结构相同，迟到的选择不会写盘；`mergeText` 取消后等待算法回调收尾，迟到结果被拒绝，有专门测试。
4. **弹窗逻辑复用得干净**：`confirmDialog` 泛化后，覆盖确认框与模式选择框共享收起 / 恢复 / 销毁逻辑；程序收起不会被误当作用户选择，runtime 测试矩阵完整。
5. **合并算法细节到位**：只对齐共同片段、不做全局去重，单侧片段也带标记，末尾换行差异在来源行注明；输出按字节实时计量，超限不截断；专用标记不会误伤普通 Git 标记。
6. **遵守项目约定**：业务模块不 import `electron`；IPC 签名不变；`diff` 放在 `dependencies` 且确认外置；中文文案；测试不读 `.env`、不碰真实 Bucket。

## 六、结论

- **合入前建议修复**：P1（常见规模下功能不可用）、P2（静默报告错误结果）。
- **建议同批处理**：P3–P5（分类与计数正确性），并补充第四节列出的测试。
- **后续优化**：P6–P8（性能）、P9–P10（文档与细节）。
- **风险**：没有发现会错误覆盖或丢失本地数据的路径；所有问题都是「不写盘但结果不对」或「本应合并却未合并」。
