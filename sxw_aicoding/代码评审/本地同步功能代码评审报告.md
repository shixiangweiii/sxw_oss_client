## 🔴 高危：共享 `REQUEST` 对象被 `listV2` 污染（`src/main/sync.ts:23`）

`const REQUEST = { timeout: 120000 }` 是模块级共享对象，被整个任务生命周期内的所有 SDK 调用复用。但 ali-oss 的 `listV2` 会**原地修改传入的 options**：

```js
// node_modules/ali-oss/lib/object.js:247（listV2 实现）
options.subres = Object.assign({ 'continuation-token': continuation_token }, options.subres);
```

实测确认（真实 SDK + 本机 HTTP 服务）：只要云端对象超过一页（>1000 个 key，分页真实发生），`REQUEST` 就会残留 `subres: {'continuation-token': '<最后一页的token>'}`，导致同一次任务内后续所有请求 URL 变成：

```
REQUEST after listV2 pages: {"timeout":120000,"subres":{"continuation-token":"tok-abc"}}
HEAD /k1?continuation-token=tok-abc
GET  /k1?continuation-token=tok-abc
```

影响链路（均位于 `src/main/sync.ts`）：

| 位置 | 调用 |
|---|---|
| 368 / 376 / 464 / 484 | `client.head(entry.key, REQUEST)` |
| 352 | `client.getStream(key, { ...REQUEST, headers })`（spread 只复制 `subres` 引用） |
| 471 / 497 | `client.put(entry.key, …, { ...REQUEST, … })` |

后果两种可能，都不好：

1. **签名失败**：V1 签名下客户端把该参数计入了 string-to-sign（`createRequest.js` 中 subres 参与 `authorization`），服务端若不把 `continuation-token` 列为对象接口的签名子资源 → `SignatureDoesNotMatch`，任务内每个文件都失败；
2. **脏状态泄漏**：即便服务端忽略未知参数，也属于把分页状态泄漏进无关请求，行为不可控。

**测试没抓到的原因**：`sync.test.mjs` 的分页用例用的是手写 `Cloud` 替身（自己实现 `listV2`，不污染 options）；唯一用真实 SDK 的用例只有 1 个对象（单页）。这是真实的测试盲区。

**修复建议**：给 `listV2` 传独立的 options 字面量（如每次 `{ timeout: 120000 }`），保持 `REQUEST` 不可变；并补一个「真实 SDK + >1 页列表 + 后续 head/get」的回归用例。multipart 系列函数（`initMultipartUpload`/`uploadPart`/`complete`/`abort`）内部会拷贝并覆盖 `subres`，不受影响。

## 🟡 中危

### 1. `recover()` 失败会永久堵死同步，且报错无路径（`sync.ts:276`、`syncFiles.ts:140`）

每次任务开头 `await this.temps.recover()`，一旦某条残留记录无法确认归属（用户/其他进程往临时目录塞了文件、`sync-temp-files.json` 损坏），不仅本次任务 fatal，**之后每一次同步都在同一处失败**，没有自愈路径。

且 fatal 分支的 issue path 是 `this.state?.currentFile ?? ''`（扫描期恒为空字符串），用户看不到该清理哪个目录，只能去 userData 翻清单。

**建议**：`run()` 内的 recover 失败可考虑降级为警告继续（清理不是任务的前置条件）；至少把具体路径写进 issue。

### 2. 下载统一落盘为 0600 权限（`syncFiles.ts:122`）

```ts
createWriteStream(destination, { flags: 'wx', mode: 0o600 })
```

所有下载新增/覆盖的本地文件都变成 owner-only。方案说「不同步本地权限」，这里实际是**强制施加 0600**，覆盖已有文件时还会改变其原权限；README 未提及。共享目录/多用户场景下会意外。

**建议**：至少文档化；或对「覆盖」场景保留原文件 mode。

### 3. 下载在最开头就创建父目录（`sync.ts:365`）

`download()` 第一步 `safePath(root, entry.key, true)` 就把中间目录建好了，之后即使传输失败/取消，空父目录残留不清理。与「失败或取消时清理临时产物」的预期有轻微偏差，会在失败任务后留下空目录骨架。

## ✅ 做得好的地方

- **互斥原子性**：`reserveSync` / `withTextWrite` 检查与占用之间无 await，主进程单线程下无 TOCTOU；同步/保存在 IPC 边界双向拒绝，冒烟测试有覆盖
- **临时文件归属设计**：先持久化清单再 mkdir（崩溃顺序安全）、owner 标记校验、拒绝按前缀批量删除，比方案要求的还严谨
- **路径安全**：逐级 lstat 拒绝符号链接、NFD/大小写按实际卷探测（`volumeRules`）、下载前后双重 `safePath` 复核 + `sameFile`（dev/ino/mtimeNs）竞态检测、`O_NOFOLLOW` 打开快照
- **ETag 语义正确**：只用作版本绑定（If-Match）不用作内容 hash；同大小才读云端算 SHA-256，README 如实声明了「跳过仍有读取流量」
- **分片上传**：显式批次 + `allSettled` 等待在途分片、partNumber 升序提交、abort 404 容忍、清理失败单独上报，与方案逐条对应
- **渲染层竞态**：revision 全局单调去重、先订阅再拉取、`sessionId` / `treeId` / `directoryRequests` 三层代次守卫，配套状态测试覆盖了乱序/旧任务响应
- **IPC 边界**：四步登记齐全（constants → types → ipc → preload），`sandbox` / `contextIsolation` 未破；sendSync 仅用于 beforeunload 的同步决定，合理

---

## 总结

整体实现质量高于方案基线，边界处理（取消协调、临时文件、路径安全、互斥）都很扎实。但存在一个会在真实大 bucket 上必然触发的高危 bug：

> **`REQUEST` 污染**——云端对象超过 1000 个（分页真实发生）即中招，任务内所有 head/get/put 请求携带脏 `continuation-token` 查询参数，轻则行为不可控，重则全量 `SignatureDoesNotMatch`。

建议优先级：

1. 🔴 修复 `REQUEST` 共享污染，补「真实 SDK 多页列表」回归用例
2. 🟡 `recover()` 失败堵死后续任务 + 报错无路径
3. 🟡 下载文件 0600 权限未文档化
4. 其余低危项按需处理
